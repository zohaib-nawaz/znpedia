## 1. Yeh practice kya hai?

<Callout variant="tip" title="Rule">

**Koi secret kabhi commit nahi hota. Secrets environment variables ya secret manager se aate hain, aur repo mein sirf `.env.example` hoti hai jis mein naam hain, values nahi.**

</Callout>

Secret har woh value hai jis se koi aap ke system mein aap ban kar ghus sake: database password, API key, JWT signing secret, webhook secret, `.pem` private key, cloud service account JSON.

Code sab ke saath share hota hai: teammates, CI, kabhi kabhi poori duniya. Secret sirf us machine tak jana chahiye jahan app chal rahi hai.

## 2. Kyun zaroori hai?

Git history kuch nahi bhoolti. Aap ne `.env` commit ki, agle commit mein delete kar di, lekin purane commit mein woh ab bhi parhi hai. Public repos ko bots minutes mein scan karte hain aur keys use karna shuru kar dete hain.

<Callout variant="note" title="Real incident">

Ek team ke security audit mein nikla ke kai repos mein bhari hui `.env.production` files tracked thin. Repos private the, is liye kisi ne dhyan nahi diya. Lekin har purana contractor, har laptop aur har CI cache ke paas production database ka password tha. Fix sirf file delete karna nahi tha: har key rotate karni pari.

</Callout>

<CompareTable leftTitle="Secret code mein" rightTitle="Secret env mein">

Har clone ke saath key bhi copy hoti hai | Key sirf deploy environment mein hoti hai
Leak ho to poori history saaf karni parti hai | Leak ho to sirf ek value rotate hoti hai
Dev aur production ki key ek hi | Har environment ki apni key
Naya developer ko pata nahi kaunsi value kya hai | .env.example batata hai kya chahiye aur kyun
Key badalne ke liye naya commit aur deploy | Key badalne ke liye sirf env update

</CompareTable>

## 3. Kab follow karein?

| Level | Kitna zaroori | Kyun |
| --- | --- | --- |
| **Learning project** | Pehle din se | Free tier keys bhi leak ho kar billing ya ban ka sabab banti hain, aur aadat abhi banti hai |
| **Production code** | Bilkul non-negotiable | Ek leak poore customer data tak rasta khol deta hai |
| **Senior level** | Scanning, rotation aur access review ka system banana | Rule yaad rakhna kaafi nahi, tooling usay enforce kare |

## 4. Bura vs acha code

### Bura

```ts
const stripe = new Stripe("sk_live_51Hx...realkey");

export const db = postgres("postgres://admin:SuperSecret123@db.example.com/app");
```

```bash
git add .
git commit -m "add payments"
```

Key code mein hai, aur `git add .` ne `.env` bhi utha li hogi.

### Acha

`.gitignore` saari env files ignore kare aur sirf example wapas include kare:

```bash
.env*
!.env.example
```

`.env.example` commit hoti hai, values khaali aur har line par note:

```bash
DATABASE_URL=
STRIPE_SECRET_KEY=
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=
CRON_SECRET=
```

App boot par check kare ke sab values maujood hain, taake missing key production mein pehli request par nahi, deploy par hi pakri jaye:

```ts
import { z } from "zod";

const schema = z.object({
  DATABASE_URL: z.url(),
  STRIPE_SECRET_KEY: z.string().startsWith("sk_"),
  CRON_SECRET: z.string().min(32),
});

export const env = schema.parse(process.env);
```

### Farq kya hai?

| Cheez | Bura | Acha |
| --- | --- | --- |
| Key kahan hai | Source code mein | Environment mein |
| Naya developer | Guess karta hai | `.env.example` parhta hai |
| Missing key | Runtime par ajeeb error | Boot par saaf error |
| Leak ka asar | History purge aur panic | Ek value rotate |

### Public prefix ka matlab

Next.js mein `NEXT_PUBLIC_` (aur Expo mein `EXPO_PUBLIC_`) wala variable browser bundle mein chala jata hai. Matlab woh **har user ko bheja** jata hai. Wahan sirf publishable keys rakhein, kabhi secret key nahi.

## 5. Kaise apply karein?

<Flow title="Naye project mein setup">

.gitignore mein .env* ignore aur .env.example include
↓
.env.example mein har variable ka naam aur note
↓
Boot par env schema se validate
↓
Commit se pehle secret scanner chalayein
↓
CI mein bhi wohi scanner
↓
Production secrets sirf hosting ya CI secrets settings mein

</Flow>

Secret scanning ke liye `gitleaks` jaisa tool commit se pehle locally aur har pull request par CI mein chalta hai. Insaan bhool jata hai, scanner nahi.

Agar secret leak ho jaye to order yeh hai:

<Flow title="Leak response">

Secret ko provider par rotate karein (naya banayein, purana band)
↓
App mein naya secret lagayein
↓
Git history se purge karein
↓
Provider par confirm karein ke purana secret ab kaam nahi karta
↓
Team ko usi din batayein: kya leak hua, kab, kya rotate hua

</Flow>

Rotate pehle kyun? Kyunki purge leak ko wapas nahi le sakta. Jis ne clone kar liya, us ke paas key hai.

## 6. Exceptions aur common mistakes

**Kab rule nahi lagta:** publishable keys (jaise payment provider ki publishable key, ya database ki anon key jab row level security on ho) public hone ke liye bani hain. Woh `NEXT_PUBLIC_` mein ja sakti hain. Local dev ke dummy values bhi secret nahi, lekin unhein bhi `.env` mein rakhein, code mein nahi.

<Mistake
  title="Leak ke baad sirf file delete karna"
  why="Delete commit ke baad bhi purane commit mein secret maujood hai, aur jis ne pehle clone kiya us ke paas bhi."
  better="Pehle provider par rotate karein, phir history purge karein, phir confirm karein ke purani key mar chuki hai."
/>

<Mistake
  title="Secret key par NEXT_PUBLIC_ lagana taake client se call ho jaye"
  why="Woh key JavaScript bundle mein har visitor ke browser tak pohanch jati hai."
  better="Secret wali call server par karein (route handler ya server action) aur client sirf us endpoint ko call kare."
/>

<Mistake
  title="Seed script, test helper ya shell script mein default password"
  why="Yeh files bhi commit hoti hain, aur aksar inhi mein asli credentials chhup jate hain."
  better="Har jagah env variable parhein aur missing ho to saaf error dein."
/>

<Mistake
  title="Secret ko log ya chat mein paste karna"
  why="Logs aur chat history bhi stored data hai jo bahut log parh sakte hain."
  better="Logger mein sensitive keys scrub karein aur secrets sirf password manager ya secret manager se share karein."
/>
