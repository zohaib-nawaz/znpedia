## 1. What is this practice?

<Callout variant="tip" title="Rule">

**An app goes live for real users when every item on this checklist is either true or skipped in writing, with a reason.**

</Callout>

This is the last chapter of the course. It is not a new concept, it ties the earlier chapters together in one list. Each item links to the chapter where the "why" and "how" are explained.

## 2. Why does it matter?

On launch day your mind is on the feature, not on health checks and backups. That is why even pilots and surgeons use checklists: experience does not replace memory.

<Callout variant="note" title="Real pattern">

An app launched. On the first night the payment provider's webhook failed, but nothing showed in the logs because errors were being caught and swallowed. In the morning it turned out 200 orders were stuck in "pending". A health check, error alerting and "deny and log on error" were all on this checklist, and nobody had looked at them before launch.

</Callout>

<CompareTable leftTitle="Launch without a checklist" rightTitle="Launch with a checklist">

Whatever came to mind got checked | Every area checked systematically
Users tell you about the first incident | The health check and alerts tell you first
There is a backup, probably | The backup was restored as a test
Secrets somewhere in the code | Scanner clean, everything in env
No rollback plan | Going back to the previous release is tested

</CompareTable>

## 3. When to follow it

| Level | How important | Why |
| --- | --- | --- |
| **Learning project** | The security and secrets part | Even a portfolio project is on the public internet |
| **Production code** | The full list, before every launch and big release | Real users, real data, real money |
| **Senior level** | Extend the list for the project and automate it | Lower and more predictable risk on every release |

## 4. Bad vs good code

### Bad: launch plan

```bash
build passes on my machine, deploying friday evening
```

### Good: launch plan

```bash
launch: orders v1, tuesday 11:00
ci: green on main, all stages
security: secret scan clean, headers set, cors allow-list, auth tests pass
data: migration dry run ok, backup taken and restore tested on staging
ops: /api/health returns 200, error alerts go to the on-call channel
rollback: previous release kept, switch back tested on staging
owner during launch: one named person on call for two hours
```

### What is the difference?

| Thing | Bad | Good |
| --- | --- | --- |
| Timing | Friday evening, nobody will be around | A working day, the team is present |
| Verification | On my machine | On CI and staging |
| Backup | Not mentioned | Tested down to a restore |
| Rollback | None | Tested |

## 6. Exceptions and common mistakes

**When the rule does not apply:** an internal tool with five users and no sensitive data does not need the full list. Even so, do not skip the security and backups part. Whatever you skip, skip it in writing and with a reason.

<Mistake
  title="Deploying on Friday evening"
  why="If something goes wrong nobody is around over the weekend, and users suffer for two days."
  better="Deploy on a working day, morning or afternoon, when the team is available for the next few hours."
/>

<Mistake
  title="Having a backup but never restoring it"
  why="Many backups turn out to be corrupt or incomplete at restore time."
  better="Restore on staging and check that the data comes back."
/>

<Mistake
  title="Treating the checklist as a one-time job"
  why="Every big release brings new risks, and the first launch's list goes stale."
  better="Run the list again before every big release and extend it by learning from new incidents."
/>
